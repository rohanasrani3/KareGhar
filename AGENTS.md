# KareGhar repository guidelines

KareGhar connects customers posting demands with artists. The tagline is “Empowering artisans. Enabling businesses”. Keep the existing warm paper, indigo and saffron palette. The visual system is direction D, "Loom, photographed" (Hallmark redesign, stamped at the top of src/app/globals.css): Libre Caslon Display heads at 32px and up over Hanken Grotesk, Tiro Devanagari Hindi and Noto Sans Devanagari for Hindi, square corners, thin rules, no shadows, colours and fonts only through the @theme tokens, no tracked-capital labels or eyebrows, no middle-dot meta strings. Use the server-side function index below before introducing new abstractions or queries. Update this file and docs/API.md in the same change as the corresponding contracts.

## Product rules

- Use “demand” for customer requests everywhere in the interface (Hindi: “माँग”), “Demand board” for discovery with “Find Demand” in the main navigation (Hindi: “माँग खोजें”), “proposal” for artist responses, and “Work history” for the private workspace. Keep existing `/commissions` routes, Server Actions and TypeScript identifiers compatible. Physical storage uses `demands`, `demand_state`, `demand_events`, `demand_ratings` and `demand` foreign-key columns after migration 008.
- Only the owning customer can rate a Done demand after the artist submits the finished work, from 1–5 stars. Selecting a proposal alone must never enable rating. One editable rating per demand; artists and other customers cannot rate it. Ratings do not change completion rankings. Public profiles/directories show the artist's average and rating count, including private completions. Individual work ratings follow the finished output's visibility. Samples cannot be rated.
- Keep photo attribution at the bottom of the shared footer through a clearly labelled Photo credits link to the full photographer/source/licence catalogue. Do not overlay credits on the homepage photos or craft tiles.
- Use the full original `public/kareghar-logo.png` in the header. The browser tab uses only its house illustration: transparent `public/kareghar-icon.png` (256×256) plus `src/app/favicon.ico` with 16, 32, 48, 64, 128 and 256px frames. `src/app/layout.tsx` declares both icon URLs. Preserve the original artwork, proportions and transparency; exclude the wordmark and tagline from the tab icon. Logo explorations under `design/logo-options` are archived concepts, not the active brand.
- In a populated portfolio, keep the blue top-right **Add work** button as the only add control. Do not restore the bottom **Add more work** tile. Preserve **Add your first work** in the empty state and the existing edit/remove dialog.
- The homepage process describes posting a demand, contacting the artist to agree on scope/price/timing/payment, and rating the artist after finished submission. Preserve the approved homepage and footer wording recorded in `CHANGELOG.md`, with matching Hindi copy. The footer explains the marketplace's folk-art purpose and the meaning of the Sample tag (see the latest CHANGELOG entry).
- Public signup creates exactly one customer or artist role per username. Login email is private. Profiles expose name, optional company, bio, explicitly supplied public contact, external links and optional photo.
- Customers post demands. Artists send one private proposal per demand. Only the customer may select a proposer and publish or hide the finished output. Finding → In-progress → Done: an assigned artist’s finished submission automatically marks Done and enables customer ratings. Publication is independent.
- There is no customer acceptance of finished work, no fourth acceptance milestone and no supported `accept` workflow action. Accepting an artist's proposal still selects that artist. Work and payment happen directly between the participants; uploading finished work records the result on KareGhar. Legacy finished-work approval timestamps/events stay stored for compatibility but are omitted from the read contract, timeline and unread notifications.
- Count Done commissions with a nonempty finished submission for overall, category and per-form rankings, including private completions. Pilot sample records count toward rankings and ratings and keep their small Sample tag, but Impact counts real activity only (sample=0); never describe sample fees as verified earnings. Tied artists share a rank. Zero completions have no displayed rank. Adding ordinary portfolio entries does not increase rank.
- Only trusted backend code designates sample records. Mark sample artists and briefs on public pages. Generated briefs are read-only.
- Public commission discovery shows open and completed work, not work in progress. Hide the current user's own listings; route their work and proposals through private History. History messages and proposal quotations are visible only to the customer and the relevant artist; never add an admin override.
- Artists choose the offered fee or a custom quotation and may edit an active proposal for 15 minutes after creation. Both proposal and selection require contact-before-work acknowledgment. Selection locks the agreed quote. Customers may cancel a selection before finished submission, preserving its audit trail and reopening the demand.
- Commission output format is required; reference image is optional. Reference media follows the brief's visibility. Submitted and archived cancelled outputs remain participant-only until explicitly published. Finished work displays inline.
- Account deletion requires the current password and typed DELETE confirmation. Block deletion during active work; anonymize the account and invalidate sessions while retaining counterpart commission history. Public discovery and login exclude deleted accounts.
- Existing categories are stable. Artists add new forms by adding portfolio work. Both discovery pages use the same catalogue and dependent filters.
- English/Hindi is a site-wide cookie preference. Localize interface text, including form feedback. Preserve authored text. Impact shows posted demands, selected proposals, connected artists, customers and agreed demand value. Work and payment happen directly; do not report a completion rate or verified earnings.

## Runtime and verification

Next.js 15 App Router, React 19, TypeScript, Tailwind 4 and Zod. Use Node 24 for local SQLite. Run npm ci, npm run lint and npm run build inside firstship. See README.md for deployment settings. Never commit credentials or local accounts/uploads. Keep cloud data in Supabase PostgreSQL and a private Supabase Storage bucket. Render is the planned pilot host. Target zero recurring cost within provider quotas.

Apply PostgreSQL migrations 001–008 in order, once per migration, before deploying this version. Historical migrations 001–007 remain unchanged. Migration 006 adds protected customer ratings; 007 upgrades existing in-progress demands with submitted output to Done, preserving files and sharing choices; 008 renames demand storage and `accepted_at` to `legacy_accepted_at`, preserving records, audit events, constraints and access controls. Apply 008 before running this code against an existing PostgreSQL database. Local SQLite applies these upgrades automatically and idempotently using `schema_migrations`. Do not remove legacy columns or audit rows as part of this upgrade. See README.md and docs/API.md for deployment details.

Smoke-test signup for both roles, private proposals and quotations, owner-only selection/cancellation, participant-only messages, media before and after publication, and rankings and rating availability immediately after a finished submission. Verify category/form filters and reset, both languages, photo updates/removal, cancelable profile editing, portfolio editing, deletion/session invalidation, and clearly tagged sample inclusion. Use separate sessions for a customer, an artist and a visitor. KAREGHAR_DATA_DIR may isolate local QA data from the default .kareghar directory.

Run `npm run test:experience` for migration, authorization, rating and impact regressions, and `npm run test:security` for persistent attempt budgets, session invalidation, upload validation, media permissions/ranges and deleted-account moderation. Check that proposal selection does not enable rating, submission does, private scores follow media visibility, and changing a rating does not change ranking. For branding changes, verify the page's icon links, both image responses and decoded ICO frames. A successful HTTP icon check is not a claim that a particular Chrome session has refreshed its cached icon.

For PostgreSQL dialect, migration and permission checks, install the optional runtime with `npm install --prefix .kareghar/pg-audit --no-audit --no-fund @electric-sql/pglite`, then run `node scripts/test-migrations.mjs` from the project root. `PG_AUDIT_MODULE` can point to another installed PGlite module entry. This suite uses in-memory PostgreSQL, stub Supabase roles/storage metadata and isolated framework/storage boundaries. It checks migrations 001–008, legacy records, foreign keys, constraint/index names, RLS/grants and the real application queries/actions. It does not connect to the deployment database or exercise hosted Supabase Storage or concurrent PostgreSQL connections.

Keep `.kareghar/`, `.env*`, dependencies, generated builds and TypeScript cache files out of Git. `.kareghar` contains persistent local accounts/uploads as well as disposable QA directories; never clear the whole directory to repair tooling. ESLint and TypeScript exclude it. Use a distinct `KAREGHAR_DATA_DIR` for each browser/production smoke test. Restart long-lived application processes after a schema upgrade: the shared database connection survives development hot reload and does not rerun initialization automatically.

Use a stable `NEXTAUTH_SECRET` and the correct `NEXTAUTH_URL` for the running origin. Hosted deployment also requires server-only `DATABASE_URL` with TLS, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. `KAREGHAR_LOCAL=1` permits SQLite in a local production-build smoke test; it is not a hosted deployment setting. Do not seed connected PostgreSQL unless `KAREGHAR_SEED_SAMPLES=1` is intentional. Stop only the preview processes started for the task; Windows native-module locks may require stopping those processes before reinstalling dependencies.

Maintain the patched dependency overrides in `package.json`: PostCSS 8.5.33, TypeScript ESLint parser/plugin 8.72.2, and minimatch 11.0.8 scoped to typescript-estree. Keep `eslint-config-next` aligned with Next.js (currently 15.5.29). Do not remove overrides or apply an unchecked `npm audit fix`: compatible-range resolution previously downgraded lint tooling to an ESLint-incompatible version. After dependency changes, run `npm ci`, `npm audit`, lint, TypeScript, regression suites and the production build. A zero-vulnerability audit result is a dated dependency check, not a guarantee of application security.

The 15 November 2026 audit passed clean dependency installation, lint, TypeScript, both SQLite regression suites, the in-memory PostgreSQL rehearsal, the production build and anonymous production HTTP checks for pages, APIs, protected routes, headers and assets. Browser checks covered both roles, profile Cancel, portfolio upload, private quotations/messages/read markers, selection, submission-driven completion and customer rating, with English/Hindi and phone/tablet/desktop layouts. Hosted migrations, real Supabase Storage and true simultaneous PostgreSQL transactions still require deployment-environment verification. Pushing source to GitHub does not apply migrations or deploy the application.

## Security and concurrency invariants

- Keep mutations and audit events in one transaction. For updates to an existing demand, lock that row first, then lock only the relevant participant accounts in sorted ID order with `lockAccounts`. After waiting for locks, read the current session and participant/pause state again before deciding a transition. Keep this ordering consistent across selection, submission, cancellation and messages; do not introduce reverse lock ordering for existing-demand writes. Creating a new demand may take the customer/session lock before inserting its new row.
- Moderation locks the actor and target in sorted order, rechecks effective state, appends the event and increments the target's base revision. The effective session version includes the base revision plus the latest moderation sequence. Suspension/restoration must invalidate in-flight stale writes as well as subsequent requests.
- Account deletion takes the account/session lock before checking active work in a fresh statement. Profile changes and deletion read the superseded photo key under that lock. Portfolio edits compare the previous file URL in the update predicate and return `conflict` on concurrent replacement; clean up any losing upload without deleting the winning file.
- Keep agreed quotations private: only the customer and assigned artist receive the selected fee. Other readers, including competing proposers, receive the original public budget. Individual ratings follow finished-output visibility; public artist aggregates may include private completions. Never widen history, message or private-media access for admins.
- Login and current-password checks use persistent budgets through `takeAttempt`; password change and deletion share the same per-account budget. Bound inputs before Argon2 verification, fail closed on malformed hashes, and retain revision checks after password verification.
- Validate uploaded bytes and the 5 MiB limit on the server. Profile/reference uploads are JPEG, PNG or WebP. Finished image/audio/video demands require the matching supported media type; physical/live/other demands accept supported evidence files. Never trust the browser MIME type or a browser-supplied existing media key.
- Accept only UUID media keys with supported extensions. Recheck authorization before every full or ranged media read, including after visibility changes. Keep private/no-store headers, single-range 206/416 behavior, missing-file 404s and storage-failure 503s. Samples alone may use trusted public fixture paths.
- Profile and portfolio external links must be HTTP(S) without embedded credentials. Sanitize legacy JSON/URLs on reads too; malformed or unavailable media should render a useful fallback. Keep frame/object/form restrictions, no-sniff, referrer and permissions headers in `next.config.ts`; the focused CSP does not replace escaping or authorization.

## Responsive and interaction invariants

Preserve 16px form inputs on narrow screens and coarse pointers to avoid mobile browser zoom, 44px gallery/dialog/rating targets, wrapping headings/toolbars/actions, and gallery `min-width: 0` / `max-width: 100%` constraints from the first paint. Check long authored names, quotations, links and messages, Hindi text, both gallery views and modal scrolling at narrow widths. Do not fix overflow by hiding required controls.

Authentication navigation must still work when sessionStorage is unavailable; notices are optional. Preserve newer message text typed while an earlier message is sending. Profile Cancel must discard drafts, portfolio replacement uploads must remain required when replacing an external link, and invalid reference previews must show localized feedback. Deleted/suspended proposers retain historical context but cannot be selected or messaged while unavailable. Deleted accounts have no restoration control; moderation metadata must not link to inaccessible private or paused demand details.

## Admin access and reversible suspension

Public signup always validates customer/artist. A backend-only admin grant supplies the effective admin role. Admins can view the customer/artist dashboard summary, including public profile fields, portfolio links and commission metadata. Never add an admin override to proposal or unpublished-media authorization. Public reads hide suspended accounts and affected listings. Active participants retain their history and see a pause notice. Completed commission history is preserved. Restoration requires fresh login.

| Module and function | Inputs → output | Purpose |
| --- | --- | --- |
| scripts/create-admin.mjs | username, optional email → generated password on stdout | Atomically creates a new account and admin grant. Never promotes a pre-existing username. |
| scripts/init-local-db.initializeLocalDb | SQLite database → void | Apply baseline and incremental migrations, including the submission workflow upgrade, for local startup and provisioning. |
| server/moderation.requireAdmin | () → active server-verified admin or 404 | Protect every moderation read and mutation. |
| moderationAccounts / moderationHistory | () → account summaries / audit events | List public identifiers, suspension/deletion status, open demands and moderation history. |
| moderationDashboard | target ID → public profile fields and demand summaries | Read-only dashboard, including suspended/deleted accounts. Only public, unpaused demand detail links are offered; deleted accounts cannot be restored. |
| server/moderation-action.moderateAccount | state, FormData(target, version, action, reason, confirm) → feedback | Append a suspension or restoration atomically. Reject stale sessions, stale decisions, self-targets and sample accounts. |

The account_state view derives the effective role, suspension and session version. Each audit event changes the target's session version. demand_state derives paused from both participants. The unique global moderation sequence serializes conflicting decisions. A valid active admin other than the target must exist at the time of a suspension, preserving the last active admin. Deleted accounts cannot be restored through moderation.

Both discovery directories use DirectoryTile(href, title, cover?, formLabel, children, footer, action) for artwork-first tiles. Real briefs show a supplied reference image, published media, or the form label. The specific-form filter is disabled until a category is selected. Clear filters resets every selection. Impact shows four connection-based totals, posted/finding/selected counts, average agreed fee, counting methodology and artist-directory link. Do not display a completed-demand total or completion rate. Include pilot samples and explain that their value is fictional.
Usernames preserve case at signup, admin provisioning and login. Passwords for signup and password changes must contain 6–128 characters.
A normal credentials login sends every role to the homepage (/). Newly registered artists are guided to /profile?tab=portfolio&onboarding=1. The header provides access to the profile, portfolio, private History with unread count, security, and admin moderation.
Hosts (Vercel, Render) build and serve from the default .next. A local production smoke test sets KAREGHAR_LOCAL=1 for both build and start, which uses .next-production so it cannot overwrite a running dev server's assets.
